# ModpackTools 3.3.0

Use ModpackTools directly from Nushell with native structured machine results while
keeping normal interactive output clean.

## Changes

- Adds a Nushell adapter that keeps PowerShell as the canonical engine and parser.
  Normal Nu usage shows only R3CLI presentation; the internal JSON envelope is
  consumed silently instead of being echoed back to the terminal.
- `--no-human` is the explicit Nushell machine mode. It suppresses R3CLI presentation
  and returns the parsed envelope as native Nu records or lists for scripts and
  pipelines.
- Restores automatic R3CLI colour in normal Nushell usage. The adapter forwards the
  parent Nu stderr terminal state to the PowerShell bridge, so `--colour auto`
  behaves like an interactive command despite Nushell's child-process forwarding
  pipe, while `NO_COLOR`, explicit colour modes, and redirected stderr still work.
- Adds the additive `--json` machine channel and `--json --no-human` mode to the
  PowerShell CLI. Machine responses use one schema-versioned JSON envelope on
  stdout, including structured expected errors.
- `modpack use <id>` now persists correctly for a Nushell session. The adapter stores
  the validated selection in `MODPACKTOOLS_PROJECT`, and each child PowerShell
  process inherits that state when importing ModpackTools. Later commands are not
  rewritten and no `--project` arguments are injected.
- Explicit `--project <id>` and documented positional project selectors therefore
  remain entirely under the canonical PowerShell parser and can override the
  inherited active project for one command.
- Adds the Nushell installer entry point `install-modpack-tools.nu`, using Nushell's
  lower-case kebab-case naming convention. It delegates to the existing verified
  PowerShell installation path instead of introducing a second installer engine.
- The PowerShell installer configures the Nu adapter automatically when Nushell is
  available and updates a marked, idempotent block in `config.nu` without replacing
  user configuration.
- Fixes a Nushell wrapper failure where a stale native `$env.LAST_EXIT_CODE` could
  make a successful command such as `modpack --version` appear to have failed. A
  valid structured envelope is now authoritative.
- Fixes Nushell adapter setup from the standalone PowerShell installer by moving the
  shared atomic UTF-8 writer into the filesystem helper layer loaded by the
  installer.
- Fixes redirected machine output containing non-ASCII project data. The bridge now
  pins stdin/stdout to UTF-8 and the Nu wrapper explicitly decodes captured byte
  streams, so names and filenames such as `café` or `§...` remain valid JSON instead
  of becoming a Nushell `binary` value.
- `modpack use --help` no longer risks changing Nu session state: the wrapper updates
  its environment only from an explicit successful `active_project` machine result.
- README, Nushell documentation and CI describe and exercise the complete
  PowerShell/Nushell boundary, structured output and session-state behaviour.

## Validation

The PowerShell regression suite and both installation/self-update integrations run
in CI. The Nushell job installs Nu 0.115.1, parses the adapter and Nu installer,
checks that normal commands do not leak machine payloads, exercises `--no-human`
structured output, expected errors, `modpack use` across separate PowerShell
children, help without state mutation, terminal colour forwarding, non-ASCII
request and response data, installer-driven `config.nu` setup, and the installed
command in a fresh Nushell process.

PowerShell remains the single implementation of ModpackTools domain behaviour.
Nushell is an adapter over the stable machine-readable boundary, so existing
PowerShell commands and project semantics remain compatible.
