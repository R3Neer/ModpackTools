# ModpackTools 3.4.0 — Global search and clearer CLI feedback

ModpackTools 3.4.0 makes Modrinth search useful before a project is selected, adds concise global command aliases, and makes human-facing change messages state clearly whether work is planned or already complete.

## Changes

- `modpack search <query>` now works without an active or explicit project. Project-free searches query Modrinth globally instead of failing with `Project.NotSelected`.
- Numbered results from a global search can later be passed to `modpack add <number>` after a target project is selected. Compatibility is validated against that target project at add time.
- Searches made with an active or explicit project keep the previous compatibility filtering and project-bound number scope, so a filtered result cannot silently migrate to another project.
- Adds global `-h`, `-v`, and `-u` aliases for `--help`, `--version`, and the self-update `--update` option. Command help also accepts `modpack <command> -h`.
- Nushell exposes the same aliases and global-search behaviour while keeping lowercase Nu-style option validation and the existing PowerShell bridge contract.
- Applied transaction messages now use completed wording such as `Added`, `Changed`, and `Removed`. Dry runs use hypothetical wording such as `Would add`, `Would change`, and `Would remove`.
- Content-plan removals are rendered as state transitions rather than imperative-looking instructions. Machine action values remain unchanged.

## Compatibility

Long option forms remain supported. `modpack update` still updates modpack content, while global `modpack --update` / `modpack -u` updates ModpackTools itself.

Project-filtered search references remain bound to the project and compatibility context that produced them. Global references are portable only to `add`, where normal compatibility resolution still decides whether the selected target project can install the result.

The schema-versioned machine envelope and structured transaction action names are unchanged.

## Validation

CI covers the PowerShell CLI aliases, Nushell alias forwarding, project-free search, null global search context, reuse of a global numbered result in a later project, preservation of project-bound mismatch protection, and the planned-versus-completed message contract.

The release workflow publishes only after the normal `CI` workflow succeeds on `main`, rebuilds the installable ZIP from the tested commit, expands it again, validates its module manifest and version, and only then creates the stable tag and GitHub release.
